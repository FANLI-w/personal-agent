# 一项科研要求，默认一项任务

合成输入：“已有论文和代码，想进一步完善之前投稿的研究项目，创新与实验还要加强。”

预期：整理为一项待确认任务，先沿已有工作推进，尚未阅读的论文和结果不能编造。执行步骤、交付和检查放进任务内部，不把补实验、核对代码、写作、自检分别创建成七项。目标可表达时就给草案，材料和日期可以后续补；不强加七阶段流程或问卷。普通问答仍自然回应。

用户明确说“合并成一个任务”时：同负责人旧草案的七个步骤合为一项，保留标题、目的、交付、验收和依赖次序。客户端不再把多项草案改写成一项，这句要求靠助手遵守规则完成；助手仍返回多项时，预览和确认就是多项，不静默合并、不丢弃内容。已确认的旧多任务保留原数量，不自动合并、删除或修改。

用户明确要求“请帮我创建两个任务”时按意图调整。大项目已有独立成员分工、分别交付和跟踪的需求时，助手可直接建议多项并简短说明理由，不先让用户选择模式。比较三个模型、论文多个章节、泛称“很难”，以及抱怨“为什么创建了七个任务”、引用和疑问本身都不作为拆分依据。不同成员/执行授权、不同日程或无效依赖时，不丢弃内容或自动扩大权限，说明冲突供继续调整。

合成对照：“做一个很难的模型对比，最后给我一份报告”仍优先一项；“小林独立交付数据集，小陈独立完成模型训练并交评估报告，数据集交付后再训练”可以是两项带真实前置关系的任务。界面没有一项/多项切换按钮，用户用对话调整。预览几项、明确确认后就创建几项，自动识别不等于自动创建。

性格与口吻可编辑，但不能越过客户端的创建数量、原权限、版本和明确确认规则。语言情境是维护者体验要求；本机回归检查使用合成内容，不将真实交流、安装或产品界面体验记为已验收。
