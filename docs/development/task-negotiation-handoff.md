# 任务协商与前置成果交接（设计草案，待与导师对齐）

## 背景

任务流转机制的三处后端 bug 已修复（分支 `fix/task-flow-state-machine`，commit `b6fe89b`）：

1. 「请求支持」误报「内容不存在/已失去访问权限」——block 操作要求被请求成员已有 full access，已改为只禁止 revoked。
2. 上游审阅「先拒绝后接受」导致下游永久卡死——上游 accepted 时未清除下游 dependency_impacts，已加 `resolveDownstream` 自动恢复。
3. 认领未完成前置的任务后无法明确「等待前置」——accept/claim 已改为：依赖未完成 → blocked（「等待前置任务完成」），前置完成自动恢复 ready。

另已核实无需修：审阅人残留（「我的待办」只在 `in_review + reviewer` 出现，导师已实现）。

剩余两个产品设计问题，需先对齐方向再动手。

## 问题 A：任务创建后无法继续对话修改

- 现状：确认任务后 plan 从 `draft` 变 `confirmed`，`planRequest` 拒绝非 draft 计划，规划对话锁死。
- 表现：用户无法通过对话修改任务；回复里「可打开任务跟进或修改」的「修改」无入口。
- 根因：锁死机制本意是「防止同一对话塞入新任务、污染两边内容」，但把「修改」一起锁死了。
- 待对齐：
  1. 任务创建后如何安全地继续对话修改（复用原计划？新对话？如何区分「修改」与「新任务」）。
  2. 修改如何映射到后端 `propose_change`（变更提案）。
  3. 权限：initiator / reviewer / lead 谁能改（当前后端仅 lead/initiator，不含 reviewer）。

## 问题 B：信息不足时的选项补充

- 现状：`unresolvedQuestions` 是 `string[]`，纯文本追问。
- 目标：结构化——每个问题带类型 + 候选项，前端渲染成「选项/可填写」表单，用户选择后回填继续拆解。
- 待对齐：schema 设计（问题类型、候选项、必答/可选、是否复用 DSH 的选项交互）。

## 问题 C：前置成果传递

- 现状：依赖任务 `start` 只校验「前置已完成」，不传递内容；`inputArtifactIds` 在 confirm 时 `NOT_IMPLEMENTED`；结论需审阅人手动 `retainConclusion`。
- 目标：依赖任务能读到/引用前置任务的交付物 + 结论（至少文字结论自动传递，文件传递标待办）。
- 待对齐：
  1. 传递机制：`inputArtifactIds` 实现 + 结论自动传递 + 依赖者对前置任务的摘要可见性（当前依赖者连前置任务摘要都看不到）。

## 统一方向建议

三者本质是同一套「对话式任务协商」：任务方案的创建、修改、补充、依赖交接，都通过对话 + 结构化选项完成，而不是多个独立表单。建议作为整体设计，避免拆开返工。
