# 规划聊天：回复与方案分开

2026-10-25。负责人反馈0.10.43正常发言后只有系统失败提示，右上角绿色方块也无法直观表达返回。此批保留PR103的助手身份/私人偏好与PR102的展开布局，在新分支修复回复通道和返回入口。

## 诊断与实现

只读线上记录：最近失败发生于北京时间2026-10-25 11:59:33，failure=INVALID_MODEL_OUTPUT，阶段validation、返回长度30、finishReason=stop。旧实现有意不保留模型正文，因此无法直接还原原文和具体intent；一次进一步结构查询因正文为空无法解析，没有写生产数据库。可以从源码复现两条路径：模型返回意图不匹配，或draft对应空plan，均在校验阶段失败。旧界面每句聊天都要求draft，用方案的unresolvedQuestions承载自然回复，尚未需要方案的交流容易触发这一矛盾。不能把这一诊断说成原始模型返回已被完整还原。

新客户端显式发送可选replyMode=conversation。模型协议要求非空answer，并允许plan=null：先直接回应研究问题，只有提出/调整具体步骤时才附方案。对话回复不创建空计划、不改旧方案版本、不附确认动作；真正的草案仍逐项校验，保留明确日期、成员与资料权限、版本、依赖及显式确认。新接口reply.message显示真实回复，旧草案回执仍可读；空白/缺失回复继续报错，不能填充固定话术冒充助手已回应，也没有自动付费重试。

contract0.32.0仅增量增加上述请求字段和可选reply.message；缺省不插入replyMode，旧请求幂等形状、旧客户端的旧请求/回复保持。新客户端以实际健康版本32为门槛，旧后台明确提示升级，保留消息和方案。schema026、依赖与锁保持，无迁移。

后台仍核对本人助手、私人直接会话、模型绑定及人设/记忆摘要；账号或档案变化后迟到回复不写入，实际用量保留。自然回复存既有execution_jobs.request_json的conversationAnswer，getPlanning在读取时投影message；持久化document.reply保持旧0.31形状，便于同schema镜像回退。写入回复与业务状态在同一savepoint内，失败全部回滚；旧接口不会因未知message字段无法解析已存任务。

诊断只补白名单intent、plan形状与是否存在answer，不保存模型正文、字段名、密钥或个人材料。返回按钮改为浅绿细边框的“← 返回工作台”，展开入口保留文字与上箭头，按钮文字/图标继承同一颜色，解决原灰色低对比和纯图标含义不清的问题。点击仍仅收起规划面板、恢复原工作台，不清除对话。
