## 审核发现及修正

- 原装配器读取同组所有项目规则。现在普通群聊只读群所属课题组规则；规划只带明确计划的项目约定，不读取其他项目；个人规则只跟随本人，不进入群聊。
- 原写入预算使用占位 id、累加所有项目，和装配口径不一致。改用共同 UTF-8 条目计量、真实 id；项目分别计量，发布组规则会核验各个适用项目。
- 原存量超限会删去全部组规则继续调用模型。改为明确失败；聊天把该轮记成 BUDGET_EXCEEDED，规划保留失败回执，均不调用模型，不让队列永远卡在同一条记录。
- 原个人规则页面的“修改”按新建发请求。修复为原 id/版本更新；使用既有请求幂等槽处理响应丢失，切账号/切组清草稿并拒绝晚到结果。
- 原可复用方法可无来源、修改类型，来源任务派发人显示可修改却可能被误拒。现在必须源于本人承接且已完成的任务；来源与类型固定，负责人/派发人按原审核规则处理。界面选择任务而非输入内部 id；明确后台门槛与真实读取错误。
- 原本机任务仍是另一套装配逻辑且没有个人规则。改为复用 constitution.compose，服务端返回执行者本人适用的 personalRules；共享个人任务不携带私人规则。角色、Skill 内容、模型配置及 DSH 上游源码不改。
- 任务面板区分“当前可用规则”与“上轮实际带入”，实际回执保留条目、版本和省略项；改规则仍会触发既有会话轮换，旧交接摘要须重新核对。
- 未登记主体/动作在运行时也拒绝，不再落入通用读取或批准分支。没有扩大模型写业务记录的权限。
- Docker 构建补齐 API 前的 research-skills / constitution 构建；保持固定工具及校验，收紧下载重试期限。

## Git 资料和生效规则的边界

Git 管目录、小正文、项目说明和版本；大原件继续本地或现有共享服务。选定的项目要求作为明确取用的参考材料进入任务，保留 commit/哈希。平台、课题组与个人生效约束仍来自授权 API；仓库里的文字不能自行升级为平台约束或增加工具权限。成果沿既有任务归档，再登记项目原件引用；没有自动替人审核、合并或发布。
