# 规则与记忆框架（constitution）

本文记录「三层宪法 + 权限边界 + 注入纪律」的当前实现与后续设计。目的是让同一份规则只存一处、只有一个人或模型有权改、并且进入上下文的路径可解释。

状态：框架与三处接线已完成；链路库与个人规则有独立流程；记忆侧未改。契约 **0.44.0**，迁移 **033**，未部署。

## 1. 三层与内容类

层是归属，内容是它装什么。`rank` 只用于比较覆盖关系，不落库、不进契约、不进界面。

| 层 | rank | 归属 | 收什么 |
|---|---|---|---|
| `system` | 3 | 平台级 | 通用运行规则、已知运行期通病、恶意与破坏行为底线 |
| `lab` | 2 | 课题组共享 | 课题组与项目规则、组内链路、任务上下文 |
| `personal` | 1 | 本人私有 | 个人规则、个人任务记录、本人会话 |

| 内容类 | 含义 | 归谁提供 |
|---|---|---|
| `rule` | 约束 | 平台 / 课题组 / 个人 |
| `link` | 组内提炼的可复用方法 | 课题组 |
| `skill` | 引擎提供的技能资产 | 引擎（内置或插件） |
| `memory` | 事实与状态 | 课题组 / 个人 |
| `object` | 当前工作对象（任务档案） | 任务 |
| `source` | 参考材料原文 | 资料 |

`rule / link / memory` 是宪法内容；`skill / object / source` 是方法与工作对象，不属于宪法，但共用同一套装配与预算。

## 2. 权限表

权限 = **主体 × 资产 × 动作**。动作五种：`inject`（每轮读）、`search`（按需读）、`write`、`request`（提交申请）、`approve`（批准）。

**默认值**：权限以显式授予为准——只有写明的主体才有对应动作，未登记一律拒绝。漏配表现为不可用，不会表现为越权。

批准人按作用域固定：任务级 = 派发人，课题组级 = 负责人，个人级 = 本人。

### 2.1 任务级

| 资产 | 谁能读 | 谁能写 | 谁能申请（批准人） |
|---|---|---|---|
| 方案 | 派发人、承接人 | 派发人 | 承接人、助手（派发人） |
| 任务本身（状态 / 依赖 / 优先级） | 派发人、承接人 | 派发人；承接人限推进状态 | 本人助理（派发人） |
| 邀请与承接 | 派发人、被邀请人 | 被邀请人（接受 / 拒绝） | — |
| 成果与交付 | 派发人、承接人 | 承接人 | — |
| 材料原件 | 派发人、承接人 | 派发人、承接人（上传） | 本人助理（派发人） |
| 执行记录 | 派发人、承接人 | 系统写入 | — |
| 交接与进度 | 派发人、承接人 | 承接人（自己的部分）、派发人（任务级字段） | 本人助理（派发人） |

### 2.2 课题组级

| 资产 | 谁能读 | 谁能写 | 谁能申请（批准人） |
|---|---|---|---|
| 平台规则 | 全平台 | 平台维护者 | — |
| 课题组规则 | 全组 | 负责人 | 组成员（负责人） |
| 组内可复用链路 | 全组 | 承接人提交（来源任务的派发人或负责人批准） | 派发人、承接人 |
| 任务上下文索引 | 全组 | 派发人 | 承接人（派发人） |
| 成员与助手公开档案 | 全组 | 本人 | 本人助理（本人） |
| 资料索引 | 全组 | 派发人、负责人 | 组成员（负责人） |

### 2.3 个人级

| 资产 | 谁能读 | 谁能写 | 谁能申请（批准人） |
|---|---|---|---|
| 个人规则 | 本人、本人助理 | 本人 | 本人助理（本人） |
| 个人助理记忆 | 本人、本人助理 | 本人助理（含自动压缩） | — |
| 个人任务记录 | 本人、本人助理 | 本人助理（自动写回） | — |
| 本人会话记录 | 本人、本人助理 | 系统写入，人可删除 | — |

聊天记录的编辑与撤回属平台已有功能，不在本框架内。

## 3. 装配规则

| 段 | 内容 | 预算 | 必进 |
|---|---|---|---|
| 约束 | `rule` | 12 KB | 是，超限失败 |
| 工作对象 | `object` | 20 KB | 是 |
| 事实 | `memory` | 32 KB | 否，超限记 `omitted` |
| 方法 | `link`、`skill` | 32 KB | 否 |
| 参考 | `source` | 36 KB | 否 |

- **写入侧拦截**：保存生效规则时校验总量，超过 12 KB 直接拒绝。规则是必进段，写进去就一定会挤占上下文。
- **装配侧兜底**：存量数据已超限时降级为「只装配平台规则 + 记录省略原因」，不让整轮规划或回复失败。
- **开关**：`CONSTITUTION_RULES=0` 关闭全部注入，行为回到接入前。
- **回执**：每轮打一行 `PLANNING_RULES` / `CHAT_RULES`，含课题组、作用域、字节数、规则 id 与省略数量。

作用域取值：

- 规划链路（`execution-worker.ts`）：平台规则 + 请求所属课题组的生效规则。
- 聊天链路（`chat-worker.ts`）：群聊取 `conversation.labId` 的规则；私聊与个人会话取平台规则 + 会话主人的个人规则。个人规则不进群。

## 5. 旧内容处置

原则：删重复的表达方式，不删内容与数据。同一事实只留一处权威，其余改读取方。

| 东西 | 角色 | 处置 |
|---|---|---|
| `PLATFORM_WORK_RULE` 常量 | 平台规则的唯一文本，界面与装配共用 | 系统层搬进表后降级为种子数据 |
| `work_context_records` 表 | 课题组与项目规则的数据源 | 保留，新链路只读它 |
| `work-memory.ts` 的 `packWorkContext` | 任务工作页的装配器 | 改用同一个 `compose()` 后只保留 handoff 等差异 |
| `ContextEntry` 的 7 个 kind | 把「层」和「类」混在一个枚举里 | 改为 `{layer, kind}` 后删除旧枚举 |
| `task-planning.ts` 的 `emptySchedule` / `newPlanStep` / `planningTemplate` | 产品零调用，仅测试引用 | 随时可删，连测试一起 |
| 契约字段 `WorkContext.platform` | 已安装客户端在读 | 保留字段、停止写入，等旧版本退场后再移除 |
| `needsClaim`（`PlanningAgent.tsx`） | 规划已不产出 `claim` | 只有历史方案命中，可随兼容清理一并删除 |

## 6. 未验证与风险

- 真实模型行为、界面交互、聊天侧预算断言均未在本地验证：`vitest` 在开发沙盒内因 `spawn EPERM` 无法启动，只能由 CI 覆盖。
- 旧客户端（0.10.98）把 `WorkRule.kind` 解析为严格枚举，读到 `kind='link'` 的记录会校验失败。整页报错。上线要求客户端同步升级，或在此之前不创建链路记录。
- 契约 0.44.0 与迁移 033 都需要配套部署；个人规则表为空时不影响任何既有行为。
