# 群聊普通回复的上下文与输出额度

2026-10-27。负责人提供0.10.56群聊反馈：引用协助请求后部分输入没有回复，长群聊经常超预算，而短答或新群有时可用。本批从最新main/30aaef4另开fix/chat-context-output-reserve。以下是代码及合成复现结论，不把原用户会话或真实模型原因说成已完整还原。

## 已证实的路径

- 公开0.10.56普通群聊@入口使用前端默认4000 tokens；0.10.59/PR120已改为每位助手16000 tokens/90秒。后台普通私聊的16000并不自动适用于sendChatMessage群聊接口；显式预算不得由后台擅自扩大。
- 旧式课题组群不一定在social_groups中。普通@原先随存储类别进入固定20条历史与JSON业务回复协议；合成旧群中90条较长记录可在调用模型前触发BUDGET_EXCEEDED。它不属于已使用packDialogueLayers的社交群路径。
- 对已打包的日常聊天，旧逻辑先为回复留下512/64，再填入可选历史。合成120条历史及引用协助请求的例子实际只剩914 token输出额度，尽管当前问题本身很短。
- recalled会随输入词变化，但packDialogueLayers每次都检查预算；不能直接推断为检索绕过预算。新消息使用新root预算，只有同一未发补充批次、委派链及明确重试共用原账本；不是整个群一直消耗同一剩余额度。
- 客户端引用是附在当前消息中的文本。task-support发出的协助通知resources为空，没有因为request类别额外注入任务资料。分类只影响历史摘要排序，不授予任务或工具权限。原报告中的空回复也可能涉及输出截断、供应商错误或协议验证，尚无原会话证据逐一确认。

## 改动与边界

普通群聊请求显式@目标助手且没有附加任务/资料context时，无论新旧群存储，单目标和多目标均使用自然文字回复及同一套上下文打包。显式协作资源和未@目标的高级请求继续原业务协议。仅新建请求选择该路径，已排队请求的已存模式与预算不自动改写。

先完整保留当前输入，再决定回复预留额度：当前必要输入之外有4096余量时优先预留4096，任务状态、近期消息与归档召回只使用余下额度。受限的当前输入、旧4000预算及重试保留512/64下界，不把全部余量预留而挤掉所有相关历史。当前输入本身过大仍明确拒绝，不截掉原话、不自动加预算。文件选段仍遵循原先整页/片段与输出权衡，角色、私人偏好和授权范围保持。

私有request_json新增modelInputDiagnostic，仅存预算、输入token保守上界、实际输出上限与是否放行；它不是实际用量。普通聊天也保存已有modelOutputDiagnostic的计数/结束原因/失败阶段，区分output_limit、provider_error、usage_missing、usage_limit与验证/保存失败。没有新建公共接口、表结构、模型调用或自动重试，不保存额外提示词、正文、供应商返回原文或密钥；群公开状态仍不含私人诊断。
