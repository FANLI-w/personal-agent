## 另行发现的存量数据兼容问题

只读核对截图对应计划的元数据（不记录私人正文、账号或 ID）：创建于 `2026-10-26T08:46:45.960Z`，v2，4 步全无 `status` / `missing`，待澄清问题 0、正式任务 0；历史规划请求没有新版粗骨架或状态规则。这发生在 PR163 合并之前。该旧数据没有因升级后台自动重新调用模型或补造状态。

新源码前端 `isDiscussionPlan` 有意保守地把缺省状态按讨论处理，但之前把全部步骤画成黄色待定，又只在问题数组非空时显示问题，没有区分「不知道状态」与「确实需要澄清」。这类旧数据在新界面会卡住；截图具体运行环境未核实，不能用这个数据缺口否认成品漏打包。

还发现三处实现不一致：

1. 客户端要求讨论时返回粗骨架 plan，后台更高优先级 system 仍要求讨论时 `plan:null`，可能使模型仅回复而保留旧方案。
2. Skill 文本残留“只有待定项时给完整草案”，与同事 PR 的待定也讨论不一致；按负责人确认统一为 PR163。
3. 隐藏创建按钮没有覆盖文字确认/helper/直接确认 API；getPlanRequest 的投影还会重新补 confirm 动作，仅修改 worker 保存值不够。

这些是源码和本地回归证明的问题，不把它们都说成已经在负责人账号上执行过。

## 修复行为

- 状态缺失用中性样式标为待核对，明确“原方案未标注规划状态”，不声称实验条件缺失；保留目标、步骤、版本和已有内容。
- 旧状态或讨论态没有问题时，显示原因和「按新版规则重新梳理」。只有用户点击才调用原规划发送链，携带当前 plan ID/version，沿用取消、账号隔离、幂等键和预算；不会后台自动改写旧计划或创建任务。
- 有问题时保留 PR163 的第一问和候选 chips；点击只填入输入框，不自动发送。新讨论卡不展开完整依赖/验收表单。
- system 明确粗骨架 plan 与纯对话 plan:null 的区别；每项状态和一个问题的要求与客户端/Skill 一致。仍保留用户内容，不凭空补 blocker，也不要求默认补齐日期/人手/资源。
- 文字确认和 `createPlannerTasks` 都拒绝讨论/未核对状态。helper 先核对已经成功的确认回执，因此旧操作丢回执仍能找回任务，不能因新检查把成功结果藏起来。
- 后台 `canConfirmPlan` 统一 worker 动作、读回投影和 confirmPlan：显式待定/阻塞为 INVALID_STATE；全部可执行后可由用户确认。无状态的旧手工编辑 API 保留既有结构验证兼容；这是兼容边界，不是自动判断它可执行。
- 已审阅草案几项就建立几项，仍保留版本冲突、明确确认、精确重试和任务数量规则。

讨论展示抽成 `PlanningDiscussion` 纯组件，数据和模型调用继续在原 PlanningAgent；没有另建业务接口、第二份计划或另一套聊天记录。
