# 任务拆解

## 先确定任务单位

- 能一项就一项，最多三项；动作、阶段或对象数量不构成拆分理由。
- 拆分看各部分能否独立交付、分别跟踪：同一目标下的动作与中间产出归入该项说明；只有各部分各有独立交付物、需分别跟踪，或存在真实前置关系时，才拆为多项。任务数量取最少够用者，不为展示结构增加数量。
- 不要求用户选择模式；用户明确要求合并或分开时，按其意图重写完整草案。
- 目标、最终成果与粗略步骤都明确时，整理为待确认方案。日期、能力、资源缺失时给默认建议、不占提问额度，用户给出时按用户值。
- 三者任一不明确时先给粗骨架进入讨论，不凭猜测强行拆分。每轮只提一个问题，用户回应后判断是否针对：针对则深入，未针对但给出新方向则改按新方向，两者都没有则不再追问，转向可推进内容或结束讨论。

## 任务形态与收缩

先判形态，再定切法：

- **交付型**：做完多一份能交出去的东西（正文、申请书、报告）；按产出倒推，末端就是它。
- **判断型**：做完多的是决定或共识；从现状推到「能下判断」，末端写定下了什么。

判不出来按判断型处理。粗骨架是从拆分态的步骤往回收缩出来的：

1. 先按「整理执行步骤」得到完整步骤清单；颗粒度与上限按「先确定任务单位」，这里不再重复数字。
2. 相邻两步若共享同一个未知、只有其中一个能独立验收、或后者只是前者的动作细分，就并为一项；从末端往回合并。
3. 项数到 3 或无法再并即停；每项整项判 `status`，末端成果写 `outcome`，不占项。
4. 合并后仍超过 3 项，说明这不止一份计划——提示用户拆成多个任务，不硬塞。

## 整理执行步骤

按任务形态选一个主方法：

- **按产出倒推（默认）**：先定最终交付，再列必要步骤。
- **按流程阶段**：列准备、执行、验证、交付，阶段写入说明。
- **按主题切片**：整理独立主题，有独立分工时才作为多项任务。
- **按对象切**：按对象组织步骤，对象数量不决定任务数量。
- **按推进环节**：判断型任务从现状推到能下判断，每个环节定下什么写清。

每步讲清目的、方法与可核对产出，同类动作合并；未看材料不声称已判断证据缺口；缺依据的步骤标待定，不写成完整交付。

## 回顾与两态

每项判断两件事：有没有依据给一个默认建议；缺这条信息时后续步骤是否无法开展。有依据记可执行，无法开展记阻塞，不阻断记待定；首步、最终成果、被多步依赖的中间节点缺信息记阻塞。每项标明 `status`（可执行 / 待定 / 阻塞）与 `missing`（缺依赖 / 缺信息），不凭猜测补全后强行拆分。

状态只看每项 `status`：任一项待定或阻塞就是讨论态，全部可执行才算拆分态。讨论态给粗骨架：目标一句，流程一句把步骤串联、末端用 `outcome` 点出最终成果，项不填依赖也不展开产出，待澄清的关键问题只留一个；阻塞影响的下游项一起变粗，已知部分保留。旧方案缺少状态不代表研究条件不足，先保留原内容并重新核对，不虚构一个缺项。

## 明确多项时的依赖

- 每项应有独立交付与跟踪价值，不因名称含“和/与/及”就拆。
- 依赖无环，引用的 id 均在清单内；依赖与分工分别处理，不把待认领当成依赖完成。
- 拆分不指定执行人；执行建议最多3句；多项总数建议不超过10，优先合并过碎内容。
- 粗骨架里被阻塞影响的下游项只留标题，不留依赖和产出。

## 产出前核对

默认一项，步骤与中间交付放入说明；确有分别跟踪价值时给多项及真实依赖。保留最终承接什么与完成要求，不编造事实、资源、进展或验收。讨论态不得输出完整草案，待定项标明 `status` 与 `missing`。创建仍由用户核对实际数量和内容后确认。
