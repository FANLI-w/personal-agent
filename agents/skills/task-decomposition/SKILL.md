# 任务拆解

## 先确定任务单位

- 拆分态下默认整理为一项任务；动作、阶段或对象数量不构成拆分理由。
- 拆分看各部分能否独立交付、分别跟踪：同一目标下的动作与中间产出归入该项任务说明；只有各部分各有独立交付物、需分别跟踪，或存在真实前置关系时，才拆为多项。
- 任务数量取最少够用者，不为展示结构增加数量。
- 不要求用户选择模式；用户明确要求合并或分开时，按其意图重写完整草案。
- 目标、最终交付与关键中间环节都明确时，整理为待确认任务，材料、日期、成员或资源可后续补充。
- 任一不明确时先给粗骨架进入讨论，不凭猜测强行拆分。每轮只提一个问题，用户回应后判断是否针对：针对则深入，未针对但给出新方向则改按新方向，两者都没有则不再追问，转向可推进内容或结束讨论。

## 整理执行步骤

按任务形态选一个主方法：

- **按产出倒推（默认）**：先定最终交付，再列必要步骤。
- **按流程阶段**：列准备、执行、验证、交付，阶段写入说明。
- **按主题切片**：整理独立主题，有独立分工时才作为多项任务。
- **按对象切**：按对象组织步骤，对象数量不决定任务数量。

每步讲清目的、方法与可核对产出，同类动作合并；未看材料不声称已判断证据缺口；缺依据的步骤标待定，不写成完整交付。

## 回顾与两态

每项判断两件事：有没有依据填默认值；缺这条信息时后续步骤是否无法开展。有依据记可执行，无法开展记阻塞，不阻断记待定；首步、最终交付、被多步依赖的中间节点缺信息记阻塞。每项标明 `status`（可执行 / 待定 / 阻塞）与 `missing`（缺依赖 / 缺信息），不凭猜测补全后强行拆分。

有待定项、阻塞项或目标、最终交付任一不明确时进入讨论态，给粗骨架：目标一句，流程一句把步骤串联、末端点出最终产物，步骤不填依赖也不展开产出，待澄清的关键问题只留一个；阻塞影响的下游步骤一起变粗，已知部分保留。只有全部明确标为可执行时才给可确认草案。旧方案缺少状态不代表研究条件不足，先保留原内容并重新核对，不虚构一个缺项。

## 明确多项时的依赖

- 每项应有独立交付与跟踪价值，不因名称含“和/与/及”就拆。
- 依赖无环，引用的 id 均在清单内；依赖与分工分别处理，不把待认领当成依赖完成。
- 拆分不指定执行人；执行建议最多3句；多项总数建议不超过10，优先合并过碎内容。
- 粗骨架里被阻塞影响的下游步骤只留标题，不留依赖和产出。

## 可后补项

日期、能力、资源缺失时给默认建议、不占提问额度，用户给出时按用户值。

## 产出前核对

默认一项任务，步骤与中间交付放入说明；确有分别跟踪价值时给多项及真实依赖。保留最终交付与完成要求，不编造事实、资源、进展或验收。讨论态不得输出完整草案，待定项标明 `status` 与 `missing`。创建仍由用户核对实际数量和内容后确认。
