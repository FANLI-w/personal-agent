# 任务拆解

## 两态

方案只有两种输出：**拆分态**＝每项都可执行，可以整体确认；**讨论态**＝存在待定或阻塞，只给粗骨架。

## 一、区分结果类型

- **交付型**：做完多一份能交出去的东西（正文、申请书、报告）。按产出倒推，这份东西写在 `outcome`。
- **结论型**：做完多的是决定或共识。从现状推到能下结论，`outcome` 写定下了什么。

判不出来按结论型处理。

## 二、列步骤

按结果类型选一个主方法：

- **按产出倒推（默认）**：最终成果清楚时，从成果往回列出中间产出。
- **按流程阶段**：过程型任务按准备、执行、验证、交付摊开。
- **按主题切片**：几个主题互不依赖时，一个主题一组步骤。
- **按对象切**：同一件事要做在多个对象上时，一个对象一组步骤。
- **按推进环节**：结论型任务从现状摊到能下结论。

## 三、粒度判定：拆项与并项

一个项＝一个可独立推进的产出：目的和交付各能用一句话说清。

- **拆项**：一项承担多个产出；跨两个以上互不依赖的主题；目的或交付一句话说不清。
- **并项**：产出相同；只是同一动作的两种说法；只是动作级小步，构不成一个推进单元。
- **过粗**：一句话里装了几件要分别交付的事，看不出先做什么。
- **过细**：只是动作级的小步，合起来才构成一个推进单元。

项数取最少够用：能一项承载就不拆，确需分别交付才拆多项，总数不超过 10。不让用户选择模式；用户明确要求合并或分开时，按其意图重写完整计划。

项定下来再连依赖：`dependencies` 只写前置项，依赖无环，引用的 id 都在清单内。

## 四、状态判定

每项只问一件事：缺这条信息，后续步骤是否无法开展。

- 无法开展记阻塞；不阻断记待定；信息齐、能直接做的记可执行。
- 首步、最终成果、被多步依赖的中间节点缺信息时，记阻塞。
- 每项标 `status`（可执行 / 待定 / 阻塞）与 `missing`（缺依赖 / 缺信息），不凭猜测补全后强行拆分。
- 日期、能力、资源缺失时给默认建议，不占提问额度。
- 旧计划缺少 `status` 不代表研究条件不足：保留原内容重新核对，不虚构一个缺项。

## 五、收拢成粗骨架

只有讨论态才走这一步：把共享同一个未知的相邻项收拢成一项，去掉猜出来的细节，但不删已知内容。

- 收拢到三项即停；被阻塞影响的下游项只留 `title`，不猜测目标或产物。结构标识与状态仍按应用约定保留。
- 收拢到三项仍放不下：只给其中一份的骨架，问题里问先做哪一份，其余留到下一轮规划，不硬塞。

## 六、自检

- 依赖无环，引用的 id 都在清单里。
- 每项都有 `status`；待定或阻塞的写了 `missing`。
- 若给粗骨架，只到 `title` 加预期 `deliverable`，不给完整计划。
- 分工由用户定：不指定执行人，不写认领，不假设成员已接受。
- 不编造事实、资源、进展或验收；创建仍由用户核对数量和内容后确认。
