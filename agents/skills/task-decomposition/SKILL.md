# 任务拆解

## 先确定任务单位

- 默认一项任务。用户要完善一篇论文、比较几个模型或准备组会报告，都是一件要完成的工作；多个动作、中间产出、论文数量和流程阶段不等于多项任务。
- 准备、实验、检查、写作、自检写作同一任务内部的执行步骤与检查清单，不分别变成待创建任务。只有实际需要独立分工、分别交付和跟踪，或大项目包含多个独立成果与真实前置关系时，才建议拆成多项，并简短说明理由。难度高、动作多或论文多本身不构成拆分理由；优先最少且够用的任务，不为展示流程凑数。
- 不要求用户选择一项/多项模式。用户明确说合成一项或分别安排时，按实际意图重写完整草案；既有版本、权限和正式创建确认仍服从应用规则。
- 用户在任务框说明要做的事，目标足够就整理为待确认任务；已有论文、代码和结果先沿用，材料或日期可后续补。不要把创建任务变成必须先完成的咨询问卷。
- 目标不清时最多问一个必要、简单问题，不复合追问；用户不满或卡住时先减轻负担、帮一小步，不凑阶段、不强加整套实验或审阅工作。

## 整理执行步骤

按任务形态选一个主方法，内部步骤只保留有用内容：

- **按产出倒推（默认）**：先定最终交付，再列完成它必要的步骤；如比较模型并写报告，仍是一项任务。
- **按流程阶段**：仅在确有需要时列准备、执行、验证、交付，阶段放在任务说明里。
- **按主题切片**：整理相互独立主题；有独立分工和交付价值时才作为多项任务。
- **按对象切**：可在内部按多篇论文或多个模型组织步骤，对象数量不决定任务数量。

每步讲清目的、方法和可核对的产出；同一产出、同一动作的不同说法或过细动作合并。已有目标能直接安排就先安排，不为每个动词造任务；未看材料不能声称已判断具体证据缺口。

## 明确多项时的依赖

- 每项应有独立交付与跟踪价值，不因名称含“和/与/及”就拆。
- 依赖无环，引用的子任务 id 均在清单内。依赖与分工分别处理，不把待认领当成依赖完成。
- 工作建议最多3句，未知资源和条件保留未知。拆解不指定执行人，分工由后续机制处理。
- 多项总数建议不超过10，优先合并过碎内容，不凑数量；该上限不用于强制拆分或迁移旧计划。

## 产出前核对

普通工作给一项任务，步骤与中间交付放入任务说明；确有分别跟踪价值时给多项任务及真实依赖。保留最终交付与完成要求，不编造事实、资源、进展或验收。正式创建仍由用户核对实际数量和内容后确认，不因模型生成草案就声称任务已建立。
